# ADR-0002: Explicit Language Identity, Capability-Based Language Profiles, and Fail-Closed Multilingual Routing

**Status:** Proposed  
**Date:** 2026-09-25  
**Decision owners:** LangReader Core / Vocabulary / Reader Architecture  
**Affected areas:** language detection, linguistic evidence, lemmatization, morphology, dictionaries, frequency/difficulty, vocabulary preparation, form labeling, vocabulary persistence, library aggregation, caches, validation, UI composition  
**Implementation compatibility:** Introduce a versioned semantic fingerprint; allocate fresh protocol versions at implementation time (current stable v3, experimental lexical reconciliation v7; do not reuse v4–v7)
**Depends on:** ADR-0001 — Evidence-Aware Lexical Identity and Conservative Morphosyntactic Reconciliation  
**Supersedes:** implicit English-default and `German ? German : English` language routing conventions  
**Repository baseline:** Re-audited 2026-09-26 at `cffa869586239434d30b469e5d54e5b684ce1a16`; earlier draft used `3a9c627a0aaf72558455460a5e4cc4e807d4dd78`. This remains a proposal, not an implementation or release approval.

---

# 1. Decision Summary

LangReader will replace implicit, Apple-type-driven, English-default language routing with an explicit **language identity and capability architecture**.

The central rule is:

```text
unknown language
unsupported language
missing capability
missing Apple NLP asset
provider failure
        ≠
English
```

Instead:

```text
document / occurrence
        ↓
language evidence
        ↓
resolved language identity OR undetermined
        ↓
language-profile resolution
        ↓
capability-specific providers
        ↓
available / degraded / unavailable
        ↓
feature-specific behavior
```

No language-sensitive operation may silently substitute a provider belonging to another language.

LangReader will introduce a stable BCP-47-backed language identity, separate language detection from product support, compose language-specific services through an injected catalog at the application composition root, and make every capability independently optional.

A language can therefore legitimately support:

```text
exact occurrence matching       yes
lemmatization                   yes
POS evidence                    yes
form explanation                no
dictionary                      no
frequency prior                 no
vocabulary preparation          no
```

without being described globally as either “supported” or “unsupported”.

Vocabulary preparation will become a **derived capability** requiring a validated combination of lower-level capabilities rather than a hard-coded language list.

The architecture will preserve ADR-0001's core epistemic invariant:

> Less or worse linguistic evidence may reduce resolution coverage, but must never manufacture linguistic certainty.

ADR-0002 extends that invariant from lexical identity to **language identity and service routing**.

## Review scope and acceptance

This revision changes the architecture decision only. Preserve the existing EN/DE product gates, ADR-0001 abstention rules, user-owned occurrence IDs/SRS/answers, offline reading, and both native reader families. No new preparation language, research approval, model threshold, or production code change is authorized by this document.

Implementation acceptance requires a vertical path from language resolution through provider selection, async publication, persistence, and library actions. A safe detector alone is insufficient if an old cache, backfill, duplicate check, or destructive library action can reintroduce cross-language identity.

The chosen approach is incremental: first contain unsafe routing using explicit language and conservative isolation; then compose existing providers behind small typed seams. Do not build a plugin framework, generalized dependency container, or a second persistence system.

# 2. Relationship to ADR-0001

ADR-0001 answers:

> Given a language and fallible linguistic evidence, when may LangReader claim that occurrences constitute one or several lexical items?

Its architecture is:

```text
occurrence
    ↓
linguistic evidence
    ↓
lexical anchor
    ↓
document-level reconciliation
    ↓
resolved identity / ambiguity / abstention
```

ADR-0002 answers the preceding question:

> Which language is being analyzed, and which language-specific systems are permitted to provide that evidence and downstream learning data?

Its architecture is:

```text
text
    ↓
language evidence
    ↓
language resolution
    ↓
language capability profile
    ↓
linguistic / lexical / learning providers
    ↓
ADR-0001 reconciliation
```

The decisions are complementary.

ADR-0001 must not itself become responsible for selecting English, German, French, Russian, or another provider.

ADR-0002 must not itself decide whether POS evidence is strong enough to split a lexical anchor.

The boundary is:

```text
ADR-0002
language identity
provider eligibility
provider availability
capability composition
        ↓
ADR-0001
evidence interpretation
lexical reconciliation
uncertainty
assessment identity policy
```

# 3. Why This ADR Is Necessary

LangReader is already substantially multilingual in its low-level text handling but its language semantics are spread across unrelated call sites.

The result is an architecture in which some components fail closed while others silently substitute English.

This produces two problems.

First, adding French or Spanish safely requires finding every implicit EN/DE assumption manually.

Second, and more importantly, some cross-language contamination is already possible in current code.

The problem is therefore not:

```text
"We should prepare for adding more languages someday."
```

It is:

```text
"Language identity is currently not an enforced domain invariant."
```

# 4. Current Repository Evidence

## 4.1 Unknown language currently becomes English

`VocabularyLanguageDetector.swift` contains:

```swift
package static let fallback: NLLanguage = .english
```

and effectively performs:

```swift
guard let dominant,
      supported.contains(dominant)
else {
    return .english
}
```

Therefore several semantically distinct conditions collapse into the same result:

```text
English detected                       → English
too little text                        → English
language detector inconclusive         → English
Italian detected but not trusted       → English
unsupported language detected          → English
```

This is not a conservative fallback.

It changes:

```text
we do not possess an applicable language analysis
```

into:

```text
the document is English
```

Those statements are not equivalent.

---

## 4.2 Reader state begins as English before evidence exists

`ReaderVocabularyState.swift` initializes:

```swift
var documentLanguage: NLLanguage = .english
```

So “not analyzed yet” is represented using the same value as “resolved to English”.

This prevents downstream code from distinguishing them.

---

## 4.3 Language-sensitive APIs default to English

Several current APIs contain parameters such as:

```swift
language: NLLanguage = .english
```

including the lemma resolver, occurrence matcher, and document lemma index.

This means accidentally omitting language information compiles successfully and changes semantics.

The safe API shape should make language omission impossible wherever the result is language-sensitive.

# 5. Current Cross-Language Correctness Bugs

## 5.1 Vocabulary difficulty silently defaults every non-German language to English

`DocumentVocabularyFrequencyProvider.calibrated(languageCode:)` currently contains the equivalent of:

```swift
let base = languageCode.lowercased() == "de"
    ? german
    : english
```

Thus:

```text
de → German frequency model
en → English frequency model
fr → English frequency model
es → English frequency model
ru → English frequency model
it → English frequency model
anything else → English frequency model
```

If a non-English document reaches this function, its difficulty model is not merely unavailable; it is replaced by an unrelated English prior.

That can alter:

```text
candidate difficulty
question ordering
theta estimation
predicted known probability
coverage estimate
selected deck
```

This is a structural assessment error.

---

## 5.2 Vocabulary-preparation definitions have the same fallback

`LiveVocabularyPreparationDefinitionProvider` effectively performs:

```swift
if language == German {
    GermanWiktionary
} else {
    ECDICT
}
```

ECDICT is an English lexical resource.

Therefore the provider abstraction itself says:

```text
German → German dictionary
anything else → English dictionary
```

Both live document-source branches enforce EN/DE before preparation, so correctly detected French is rejected there. This is not merely a UI guard. Detector fallback can still turn inconclusive or unsupported-language text into English, and the provider API remains unsafe independently of its current callers.

---

## 5.3 Dictionary backfill already crosses language boundaries

`ReaderWindowController+VocabularyDefinitionBackfill.swift` is more serious.

The current flow approximately performs:

```text
selected word
    ↓
try English ECDICT
    ↓ if absent
try German Wiktionary
```

regardless of document language.

This means a German word that also exists in English can receive English lexical data.

For example, German and English contain unrelated or substantially different lexical items with spellings such as:

```text
Gift
die
hat
war
fast
also
```

The first successful dictionary match is not evidence that the dictionary language matches the document language.

The reverse contamination is also possible: an English miss can fall into German Wiktionary.

This is an existing correctness defect.

---

## 5.4 Generic dictionary metadata is actually English metadata

`VocabularyDictionaryMetadataService.metadata(for:)` defaults to:

```swift
LocalDictionaryLookupService.shared
```

which is backed by ECDICT.

No language accompanies the request.

`VocabularyFrequencyBackfillService` subsequently uses this generic-looking service for stored vocabulary.

Therefore its API cannot express:

```text
this word belongs to German
```

and cannot enforce that the provider belongs to German.

---

## 5.5 Backfill completion is not provider/language scoped

`VocabularyReviewPreferences` stores essentially:

```text
document → frequencyBackfilled = true
```

But a valid completion identity is closer to:

```text
document
+ language
+ frequency provider
+ provider version
+ normalization policy
```

If the detected language changes or the provider is replaced, the old Boolean can incorrectly suppress required work.

# 6. Current Library Aggregation Loses Language Identity

The problem continues after vocabulary creation.

`VocabularyLibraryRecordProvider` currently aggregates cross-document records using approximately:

```swift
canonicalVocabularyKey(record.lemma ?? record.word)
```

with no language component.

This means:

```text
English die
German die
```

can become one library entry.

Similarly:

```text
English Gift
German Gift
```

can collide.

This contradicts ADR-0001's lexical identity:

```text
language + lemma + POS
```

because language and POS are discarded before library aggregation.

`VocabularyExportRecord` also does not currently preserve the full resolved lexical identity required to reconstruct this distinction reliably.

Therefore language identity must not stop at the NLP layer.

It must propagate through:

```text
index
→ candidate
→ saved record
→ export model
→ library model
→ aggregation
→ cache/backfill
```

# 7. Current Form Label Routing Shows the Desired Behavior

Not every current component is wrong.

`VocabularyFormLabeling` already follows the desired fail-closed rule:

```swift
switch language {
case .german:
    ...
case .english:
    ...
default:
    return nil
}
```

A French word does not borrow English grammar.

Instead:

```text
no French form labeler
        ↓
no grammatical label
```

while the underlying word remains usable.

This is exactly the pattern ADR-0002 generalizes to every language-sensitive capability.

# 8. Detection and Support Are Different Concepts

The current `VocabularyLanguageDetector.supported` set mixes two unrelated questions:

```text
What language does this text appear to be?
```

and:

```text
For which languages do we trust this particular lemma provider?
```

They must be separated.

Apple's language recognizer can expose both the dominant language and multiple hypotheses with scores. Detection therefore does not need to be restricted to the set of languages for which LangReader currently has a vocabulary product.

The correct flow is:

```text
Italian text
    ↓
detector
    ↓
Italian
    ↓
capability catalog
    ↓
Italian lemma capability unavailable/untrusted
    ↓
exact-form fallback
```

not:

```text
Italian text
    ↓
detector knows LangReader does not support Italian
    ↓
English
```

The latter corrupts language identity.

---

# 9. Language Detection Must Not Be Constrained to Product Languages

`NLLanguageRecognizer` allows applications to constrain the languages it can return.

LangReader must **not** use that mechanism simply to constrain recognition to its currently productized languages.

For example:

```text
actual Italian
supported product languages = English, German
```

must not become a competition between:

```text
English vs German
```

A detector should answer the epistemic question:

```text
What language is this?
```

The capability catalog subsequently answers:

```text
What can LangReader safely do with it?
```

Language constraints are appropriate only when independent information genuinely limits the possible languages, such as an explicit user choice or a future feature with a known language set.

---

# 10. Raw Detection Scores Are Evidence, Not Product Truth

ADR-0001 already establishes that classifier scores must not be assumed to be calibrated probabilities.

The same rule applies to language recognition.

Apple exposes candidate-language values described as probabilities, but LangReader has not validated their calibration on its own document distribution:

```text
fiction
PDF extraction
OCR text
EPUB
DOCX
technical prose
quoted foreign passages
short contexts
historical texts
```

Therefore a detection model should retain:

```text
language candidates
raw scores
sample statistics
provider/version
```

without presenting an arbitrary model score as a validated probability of correctness.

The initial ADR-0002 migration does not require inventing a new detection threshold.

Its immediate correctness requirement is simpler:

> Failure, short text, or an unsupported detected language must no longer become English.

# 11. Adopt BCP 47 as LangReader's Language Identity Standard

LangReader needs a domain language identifier independent of Apple NaturalLanguage.

The identifier should use **BCP 47 language tags**.

BCP 47 is specifically designed to identify languages and can represent language, script, region and other distinctions when needed.

Examples include:

```text
en
de
fr
es
ru
pt-BR
pt-PT
zh-Hans
zh-Hant
sr-Cyrl
sr-Latn
```

A closed enum such as:

```swift
enum VocabularyLanguage {
    case english
    case german
    case french
    ...
}
```

is therefore rejected.

It would recreate the same central-support-list problem and make script/variant distinctions awkward.

---

# 12. Introduce `VocabularyLanguageID`

Conceptually:

```swift
package struct VocabularyLanguageID:
    Codable,
    Hashable,
    Sendable
{
    package let bcp47: String

    package init?(_ rawValue: String) {
        // validate and canonicalize as BCP 47
    }
}
```

Foundation already provides BCP-47-aware language representations and canonicalization APIs, including `Locale.Language`, its minimal/maximal identifiers, and BCP-47 identifier conversion.

However, LangReader should wrap rather than persist `Locale.Language` directly.

The wrapper provides:

```text
stable storage contract
validation policy
special-tag policy
future compatibility
independence from Foundation implementation details
```

`Locale.Language` may be used inside the implementation for parsing, canonicalization, parent relationships and display.

### Construction and storage contract

BCP 47 well-formedness, registry validity, and provider support are distinct checks. A non-failable `Locale.Language` initializer is not a validator. Core owns a tested parsing/canonicalization policy; Apple locale utilities may assist the adapter but must not silently rewrite persisted identities after an OS update.

Use a single string Codable representation with validation on decode, case-insensitive equality/hash, and deterministic casing. Preserve explicit script/region/variant distinctions; do not persist likely-subtag maximization or minimization. Any registry alias mapping that changes identity is versioned. Existing `en`/`de` canonical keys and their escaping remain byte-for-byte stable.

At external import boundaries preserve malformed or unrecognized original metadata for diagnostics while leaving usable records unresolved; do not let one invalid optional language field discard the document's vocabulary. The v1 resolved-language subset excludes `und`, `mul`, `zxx`, private-use-only tags, and language-tag extensions from provider routing unless an explicit future contract supports them; preserve those raw tags as external metadata. Locale syntax such as `en_US` or `@calendar=...` is never a core language tag. Valid but unsupported concrete language tags remain identities, not English. Legacy underscore-style locale identifiers require a separate tested import conversion, not permissive core construction.

---

# 13. Do Not Throw Away Script or Region Prematurely

A language identifier must not automatically normalize:

```text
pt-BR → pt
zh-Hant → zh
sr-Latn → sr
```

Those distinctions may matter for:

```text
tokenization
dictionary content
orthography
frequency distributions
morphological providers
user expectations
```

Even within one nominal language, corpus fit matters. For example, SUBTLEX-UK predicts British lexical-decision behavior better than SUBTLEX-US in the cited evaluation, demonstrating that lexical frequency sources can be population/variety sensitive.

Therefore canonicalization should standardize the tag, not erase meaningful subtags.

Provider matching may fall back to a broader parent only when the provider explicitly declares that compatibility.

---

# 14. Special BCP 47 Tags Are Not Ordinary Resolved Languages

BCP 47 defines, among other values:

```text
und = undetermined
mul = multiple languages
```

and explicitly recommends omitting a language tag rather than using `und` where omission is possible; it also advises against using `mul` when individual language information can be represented.

Therefore LangReader domain state should represent these semantically:

```swift
.resolved(VocabularyLanguageID)
.undetermined(...)
```

rather than pretending:

```swift
VocabularyLanguageID("und")
```

is equivalent to an actual resolved language.

Likewise a mixed-language document should eventually contain separately identified regions rather than becoming one permanent lexical language `"mul"`.

---

# 15. Language Resolution Must Carry Provenance

Knowing:

```text
language = de
```

is not enough.

LangReader must know how that conclusion arose.

Conceptually:

```swift
package enum VocabularyLanguageProvenance: Sendable {
    case userSelected
    case automaticDetection
    case persistedDocumentMetadata
    case segmentDetection
}
```

and:

```swift
package struct VocabularyResolvedLanguage: Sendable {
    let id: VocabularyLanguageID
    let provenance: VocabularyLanguageProvenance
    let evidence: VocabularyLanguageEvidence?
}
```

The distinction matters because:

```text
user explicitly selected English
```

is qualitatively different from:

```text
automatic detection failed and code happened to use English
```

The former is legitimate user-provided evidence.

The latter is the behavior this ADR eliminates.

---

# 16. Model Undetermined Language Explicitly

Conceptually:

```swift
package enum VocabularyLanguageResolution: Sendable {
    case resolved(VocabularyResolvedLanguage)
    case undetermined(VocabularyLanguageEvidence)
}
```

An empty or very short document can therefore produce:

```text
undetermined
```

rather than:

```text
English
```

A document recognized as Italian can produce:

```text
resolved: Italian
```

even when no trusted Italian morphological package exists.

This is a fundamental separation:

```text
language resolution
        ≠
capability availability
```

Distinguish not-yet-analyzed, insufficient text, inconclusive recognition, and provider failure as reasons, not separate invented languages. Preserve the existing 16 sampled pages / 8 prose pages / 8,000-character budget and short-sample rule initially; do not claim that the whitespace/prose heuristic is validated for every script. Reuse a bounded sampling policy for both PDF and Web snapshots instead of making Web's first 8,000 characters a separate language authority. Unit tests inject recognition evidence; live Apple checks characterize the OS and cannot be deterministic correctness oracles.

---

# 17. Refine ADR-0001's Language Fields

ADR-0001 currently uses free `String` language fields in structures such as:

```swift
VocabularyLexicalItemID
VocabularyLexicalAnchorID
VocabularyMorphologicalAnalysisRequest
```

ADR-0002 refines that decision.

A **resolved lexical item** must contain:

```swift
VocabularyLanguageID
```

rather than an arbitrary string.

Conceptually:

```swift
package struct VocabularyLexicalItemID {
    let language: VocabularyLanguageID
    let lemma: String
    let partOfSpeech: VocabularyPartOfSpeech
    let senseKey: String?
}
```

For existing English and German keys:

```text
en
de
```

the canonical serialized key remains unchanged.

This preserves compatibility while making invalid language strings harder to construct.

---

# 18. Lexical Anchors May Exist Without Resolved Language

Unlike a resolved lexical item, an exact-surface document anchor may exist while language remains undetermined.

Therefore the ADR-0001 anchor model should permit:

```swift
language: VocabularyLanguageID?
```

or an equivalent explicit state.

It must not create a fake language merely because the anchor's canonical key needs a namespace.

An internal anchor key may use:

```text
anchor|language-unknown|surface|...
```

but `"language-unknown"` is an internal structural namespace, not a BCP 47 language tag.

A resolved lexical item still requires a real language.

---

# 19. Remove Default English Arguments From Language-Sensitive APIs

Functions such as:

```swift
resolution(
    for: word,
    language: NLLanguage = .english
)
```

are unsafe.

The desired contract is:

```swift
resolution(
    for: word,
    language: VocabularyLanguageID
)
```

with no default.

The compiler should reject:

```swift
resolve(word)
```

if language affects semantics.

Language-independent operations remain callable without language:

```text
Unicode token extraction
exact surface matching
source-range anchoring
whitespace normalization
SRS scheduling
highlight persistence
```

This produces compile-time pressure toward correct routing.

---

# 20. `NLLanguage` Is an Adapter Type, Not LangReader's Domain Model

Apple's `NLLanguage` remains useful.

It should exist behind an Apple NaturalLanguage adapter:

```text
VocabularyLanguageID
        ↓
AppleNaturalLanguageAdapter
        ↓
NLLanguage
        ↓
NLTagger / NLLanguageRecognizer
```

Application/domain APIs should not require `NLLanguage`.

This prevents:

```text
Apple happens to expose an NLLanguage value
```

from becoming equivalent to:

```text
LangReader possesses validated learning support for this language
```

Italian has already demonstrated why those statements differ.

### Module placement and the migration seam

Core owns language values/resolution, evidence and request/result contracts, compatibility comparison, normalization, lexical identity, and fail-closed feature policy. App owns Apple recognition/tagging execution, asset probes, native text acquisition, concrete service composition, and UI labels. `LeafReaderValidation` remains a one-way consumer of Core and cannot supply shipping providers or release approval.

The current detector, lemma resolver, index, and form labelers use NaturalLanguage inside Core. Extract deterministic rules into or retain them in Core; move Apple execution behind narrow evidence/analyzer protocols implemented in App. Core tests use injected evidence; Apple integration tests belong to App. Migrate each consumed seam with its tests and command-line harness callers, without moving the entire index into App or weakening portability/native-access checks. A later scoped check may prohibit NaturalLanguage imports in migrated Core surfaces once their adapters exist.

---

# 21. Introduce a Language Capability Catalog

LangReader will introduce a catalog of language profiles.

The catalog is a **composition object**, not a global service locator.

Conceptually:

```swift
protocol VocabularyLanguageCatalog: Sendable {
    func resolve(
        language: VocabularyLanguageID
    ) -> VocabularyLanguageRuntime?
}
```

A profile describes which providers can potentially serve a language.

A runtime represents the providers and capability status actually available for a particular document/session/device.

---

# 22. Do Not Introduce `VocabularyLanguageRegistry.shared`

A previous design sketch proposed something like:

```swift
VocabularyLanguageRegistry.shared
```

This ADR rejects that form.

The project's existing architecture explicitly treats `ReaderWindowController` as a composition root and moves policy into focused services/coordinators.

Language composition should follow that architecture:

```text
application bootstrap / ReaderWindowController
        ↓
construct language catalog
        ↓
resolve document language runtime
        ↓
inject runtime/providers into coordinator/index/services
```

This gives tests deterministic control over:

```text
available languages
provider failures
asset availability
dictionary implementations
frequency sources
experimental profiles
```

without mutating global state.

Immutable resource objects may still internally use shared tables where appropriate.

Provider **selection** must not depend on a hidden global singleton.

---

# 23. “Language Package” Is a Domain Concept, Not Necessarily a Swift Module

ADR-0002 does not require creating:

```text
LeafReaderEnglish
LeafReaderGerman
LeafReaderFrench
...
```

SwiftPM targets.

That would create substantial structural cost before the abstractions stabilize.

Initially, a language package/profile can simply be an immutable composition structure inside the existing Core/App architecture.

Separate modules may be introduced later if package size, dependency isolation, build time, licensing or team ownership provides a concrete reason.

# 24. Capabilities Are Granular, Not Boolean

There will be no authoritative:

```swift
isLanguageSupported: Bool
```

because “support” has too many meanings.

At minimum, the architecture distinguishes:

```text
language detection
exact token matching
lemma evidence
POS evidence
morphological evidence
lexical reconciliation
form labeling
definition lookup
general frequency/difficulty
domain-specific frequency
vocabulary preparation
speech/TTS where relevant
```

A profile can expose any subset.

# 25. Proposed Language Runtime Shape

Conceptually:

```swift
package struct VocabularyLanguageRuntime: Sendable {
    let language: VocabularyLanguageID
    let profile: VocabularyLanguageProfileDescriptor

    let linguisticEvidence:
        (any VocabularyLinguisticEvidenceProviding)?

    let formAnalysis:
        (any VocabularyFormAnalyzing)?

    let definitions:
        (any VocabularyDefinitionProviding)?

    let difficulty:
        (any DocumentVocabularyDifficultyProviding)?

    let domainResources:
        VocabularyDomainResources?

    let featureAvailability:
        VocabularyLanguageFeatureAvailability
}
```

This is illustrative rather than mandatory Swift syntax.

The important rule is that optional capabilities are explicit.

Optional providers alone must not encode every failure as `nil`. Each capability has one authoritative status derived from the selected descriptor, runtime probe, and release policy; feature availability is a read-only projection. Typed lookup outcomes distinguish found, not-found, unavailable, incompatible-request, and transient-failure; cancellation propagates separately. An empty result is not permission to choose another language. Validate request language and any lexical item's language agree before dispatch.

Reuse existing `VocabularyPreparationDefinitionProviding` and `DocumentVocabularyDifficultyProviding` as migration seams. Do not require consumers to depend on the entire runtime when one provider suffices. Descriptors and immutable evidence are Sendable; mutable Apple analyzers remain worker-local or actor-confined. Do not claim Sendable by sharing an `NLTagger` or adding unchecked conformance.

# 26. Separate Static Registration, Runtime Availability and Release Readiness

Three questions must not be collapsed.

### Registration

Does LangReader know how this capability could be provided?

Example:

```text
Russian → Apple lexical analysis provider registered
```

### Runtime availability

Can it run on this machine right now?

Example:

```text
Russian lemma model asset missing
```

### Release readiness

Has LangReader validated this capability sufficiently to expose it for a particular product feature?

Example:

```text
Russian lemma evidence exists
but vocabulary preparation is not validated
```

Conceptually:

```swift
enum VocabularyCapabilityAvailability {
    case available
    case degraded(reason: ...)
    case unavailable(reason: ...)
}

enum VocabularyFeatureReleaseState {
    case production
    case experimental
    case disabled
}
```

These represent different concerns and must remain different types/states.

---

# 27. Apple NLP Assets Are Runtime Capabilities

Apple exposes an API for inspecting tag schemes currently available for a given language and token unit, and an API for requesting missing Natural Language assets.

Therefore a language profile must not assume:

```text
NLLanguage exists
    ⇒
lemma model exists
    ⇒
POS model exists
```

The Apple provider should probe the required capabilities.

For example:

```text
German
  lemma       available
  lexicalClass available
  nameType    available

Russian
  lemma       unavailable
  lexicalClass unavailable
```

should produce different runtime capability states even if both profiles are statically registered.

A reported scheme is an availability signal, not evidence that a particular token will receive a useful or correct tag. Handle nil/empty token results and request errors even after a successful probe. Apple does not expose a stable model-content version through these APIs: record adapter policy version, OS/runtime identity, and observed scheme set as a conservative compatibility signature, explicitly marking model revision unknown. Never invent an asset hash or assume scheme presence proves corpus-level quality.

---

# 28. Missing Assets Must Degrade Capability, Not Change Language

If German is resolved but German lemma assets are unavailable:

```text
German + missing lemma model
```

must remain:

```text
German
```

It may degrade from:

```text
lemma-based grouping
```

to:

```text
exact-form grouping
```

It must never become:

```text
English
```

The same principle applies to every provider.

---

# 29. Asset Download Must Be Explicitly Product-Driven

ADR-0002 does not require LangReader to automatically request Apple language assets at application launch.

An optional future UX may offer something like:

```text
“Additional German language analysis is available.
 Download required macOS language data?”
```

on a user-triggered path.

Correctness must remain possible without the download through abstention/exact-form degradation.

Network availability therefore remains an improvement to coverage, not a prerequisite for safe operation.

# 30. Provider Matching Must Be Fail-Closed

Suppose the catalog contains providers for:

```text
en
de
```

and receives:

```text
fr
```

The result is:

```text
no matching definition provider
```

not:

```text
English definition provider
```

The same rule applies independently to:

```text
morphology
dictionary
frequency
forms
domains
```

This is the fundamental routing invariant.

---

# 31. Same-Language Fallback Is Different From Cross-Language Fallback

BCP 47 defines language-range matching and a lookup process that progressively removes less-specific subtags until a matching tag is found. It also explicitly requires an application to define what happens when no tag matches.

LangReader may use a related mechanism, but only with explicit capability compatibility.

For example:

```text
de-AT
  ↓
German dictionary declares de-* support
  ↓
de provider accepted
```

can be legitimate.

By contrast:

```text
fr
  ↓
no French provider
  ↓
en
```

is forbidden.

---

# 32. Provider Compatibility Must Be Capability-Specific

A dictionary may reasonably support:

```text
en-US
en-GB
en-AU
```

while a frequency corpus may be validated only for:

```text
en-GB
```

Therefore support ranges belong to providers/capabilities, not solely to a language profile.

Conceptually:

```swift
provider.supportedLanguageRanges
```

is evaluated when composing the runtime.

This matters because corpus-derived difficulty priors can be sensitive even to language variety and population. Frequency research finds substantial differences in estimate quality, and variation in language exposure changes where frequency effects operate.

### Deterministic provider selection

Match each capability independently. Prefer an exact declared tag; otherwise consider only explicitly compatible ranges, with script/region constraints checked before any truncation. A generic `zh` or `sr` registration is not evidence of compatibility with every script. Do not substitute a regional source for an unspecified language unless that source explicitly declares the broader use validated.

For overlapping registrations, require an explicit composition priority or reject the ambiguous capability at catalog construction; never let array/dictionary iteration order select it. A broad registration must not override an existing exact registration accidentally. No-match and ambiguity are unavailable states. The returned runtime retains the requested identity even when a provider accepts it through a broader range. Dictionary compatibility cannot broaden frequency, morphology, or lexical equality.

# 33. Language Profiles Own Language-Specific Linguistic Evidence

ADR-0001 defines the neutral evidence structure.

ADR-0002 defines who can produce it.

Examples:

### English

```text
Apple lemma/POS evidence
English-specific form rules
English lexicon evidence
```

### German

```text
Apple lemma/POS evidence
deterministic -haft fallback
German frequency-lexicon attestation
German Wiktionary morphology/flexion
```

### Italian

Current evidence indicates that Apple's lemma behavior is not trustworthy enough for the existing grouping contract.

Therefore its initial profile can legitimately be:

```text
exact form                    available
Apple language identification available
Apple lemma evidence          disabled by policy
POS/form analysis             unavailable
preparation                   disabled
```

That is much safer than making the whole application think Italian is English.

# 34. Tokenization and Morphology Must Remain Language-Extensible

The current Unicode token policy is already substantially language-neutral.

However, not every language maps cleanly from surface token to one lexical word.

Universal Dependencies explicitly separates lemma, POS and morphological features and notes that some languages require language-specific handling of fused tokens; Spanish clitic constructions are one example.

Therefore the long-term language boundary must be able to contribute:

```text
token interpretation
lemma candidates
POS candidates
morphological features
```

and not merely:

```text
NLTagger language code
```

ADR-0002 does not require replacing the current tokenizer now.

It forbids architecture that would make such replacement impossible later.

# 35. Definitions Become an Explicit Language Capability

The existing `DictionaryLookupService` interface is misleadingly generic while exposing `ECDICTEntry`, which is an English-resource-specific type.

The target interface should be resource-neutral.

Conceptually:

```swift
package struct VocabularyDefinitionRequest: Sendable {
    let language: VocabularyLanguageID
    let lemma: String
    let surfaceForm: String?
    let context: String
    let lexicalItemID: VocabularyLexicalItemID?
}

package struct VocabularyDefinition: Sendable {
    let markdown: String
    let resolvedLemma: String?
    let tags: [String]
    let provenance: VocabularyProviderDescriptor
}

package protocol VocabularyDefinitionProviding: Sendable {
    func definition(
        for request: VocabularyDefinitionRequest
    ) async throws -> VocabularyDefinition?
}
```

ECDICT-specific types remain inside the English provider.

German Wiktionary-specific types remain inside the German provider.

The same definition boundary applies to ordinary selected-word lookup: `AnswerProviderRequest`, `LocalDictionaryAnswerProvider`, `AIChatPanel+Actions.swift`, and `AIChatPanel+WordActions.swift`. The current no-AI route tries ECDICT then German Wiktionary; cached local answers can also enter an AI fallback. Carry resolved source language and compatible lexical identity through these requests/caches and inject the same definition capability. The answer's display/translation language is separate from the lexical source language. Sentence/AI conversation behavior is otherwise outside this migration.

# 36. Definitions Must Validate Their Requested Language

Even after correct composition, providers should fail closed defensively.

An English ECDICT provider receiving:

```text
language = de
```

should return an explicit programmer/runtime mismatch rather than attempting lookup.

This is defense in depth.

The composition layer prevents wrong routing.

The provider contract detects violations if wrong routing nevertheless occurs.

# 37. Dictionary Data and Difficulty Data Are Different Capabilities

Current English dictionary metadata also carries an ECDICT frequency value.

This is convenient but creates conceptual coupling.

A definition provider answers:

```text
What does this lexical item mean?
```

A difficulty/frequency provider answers:

```text
What prior should the assessment use for this lexical item?
```

Those may originate in the same dataset, but they have different semantic contracts.

ADR-0002 therefore treats them as separate capabilities.

The English profile may compose both from ECDICT internally.

The general assessment layer must not infer that:

```text
dictionary exists
    ⇒
valid frequency model exists
```

# 38. Difficulty Providers Must Declare Provenance and Language Compatibility

`DocumentVocabularyDifficultyProviding` already exposes a `VocabularyFrequencyScale` containing:

```text
sourceID
version
maximumRank
```

This is a strong beginning.

ADR-0002 extends the contract conceptually with:

```text
supported language range
normalization version
provider semantic version
```

A request incompatible with the provider's language contract must not silently receive a rank.

# 39. Remove English Default From `DocumentVocabularyFrequencyProvider`

Instead of:

```swift
let base = language == "de" ? german : english
```

provider resolution becomes something equivalent to:

```swift
guard let difficulty = languageRuntime.difficulty else {
    return unavailable
}
```

Calibration then wraps the already-correct provider.

Conceptually:

```text
language runtime
    ↓
base difficulty provider
    ↓
compatible calibration pack?
    ├─ yes → calibrated provider
    └─ no  → base provider
```

not:

```text
language string
    ↓
de ? German : English
```

# 40. Calibration Packs Must Be Bound to Their Base Model

A calibration pack should be compatible with:

```text
language
base difficulty source
base difficulty version
lexical identity algorithm
normalization policy
```

not merely a two-letter language code.

Otherwise changing:

```text
ECDICT → another English corpus
```

while retaining an old empirical calibration can silently combine incompatible scales.

The target identity is conceptually:

```text
calibration target =
    language profile
    + lexical model
    + difficulty provider
```

Retain the existing reviewed/model/item-quality gates. Compatibility is an additional requirement, not a replacement for review. Validate the pack's declared target, each item's language, duplicate lexical keys, and finite numeric parameters before building lookup tables. Invalid/incompatible packs are inert with a diagnostic; retain the compatible base prior. Record the actual pack ID/version (or explicit absence) in assessment compatibility. A reviewed flag alone never establishes release readiness for a new language or protocol.

# 41. Form Labeling Remains Optional

The existing form-label architecture already demonstrates good behavior:

language has labeler → label
language lacks labeler → nil
```

This remains.

Adding French lexical grouping must not require creating a French grammar labeler first.

Likewise, lack of a labeler must not prevent:

saving
highlighting
SRS
exact occurrence navigation

# 42. Form-Label Caches Must Eventually Use Explicit Language Namespacing

The current persistent form-label cache lacks a language column, so language is encoded indirectly into an integer cache version.

That prevents current EN/DE collisions but does not scale cleanly.

The target cache identity should be explicit:

```text
language
provider/ruleset ID
provider/ruleset version

For example:

```text

# 43. Current Unicode Token Matching Is Good; Its Naming Is Not

`VocabularyTextPolicy.isSingleEnglishWord` actually uses Unicode letter/mark properties.

It is therefore substantially more general than its name implies.

Rename it as part of an actual boundary migration, for example:

```text
isSingleWordToken
```

but do not create a standalone rename-only architectural task.

The architecture-completion plan correctly discourages changes whose only effect is moving/renaming code.

# 44. Global `de_DE` Lowercasing Is a Hidden Language Policy

`VocabularyTextPolicy.canonicalVocabularyKey` currently lowercases using:

```swift
Locale(identifier: "de_DE")
```

for every language.

That policy reflects the application’s German-oriented history; its harmlessness for all saved data has not been established. It is not a valid global multilingual normalization policy.

Unicode explicitly distinguishes language-sensitive case mapping from language-neutral case folding and calls out special behavior for Turkic languages and other cases.

Therefore ADR-0002 establishes that normalization itself is part of the language architecture.

---

# 45. Do Not Change Persisted Key Semantics Casually

Although the current `de_DE` normalization is architecturally wrong for general multilingual support, changing it immediately could change:

```text
stored grouping keys
lexical keys
dedup behavior
saved vocabulary identity
```

ADR-0002 therefore explicitly rejects an unversioned normalization rewrite.

The first migration preserves current EN/DE persistent-key behavior.

Before additional languages depend on canonical identity, LangReader introduces an explicit normalization policy/version.

Any change that affects persisted identity requires:

```text
version
migration/reconciliation policy
compatibility tests
```

# 46. Distinguish Search Normalization From Lexical Identity Normalization

One global function is unlikely to remain sufficient.

Different purposes include:

```text
caseless search
surface-form equality
lexical identity
dictionary lookup
display
```

They do not necessarily need identical normalization.

The long-term model should distinguish, conceptually:

```text
search normalization
surface normalization
lexical identity normalization
display preservation
```

Unicode language-neutral case folding can be appropriate for some internal caseless matching, while language-specific lexical semantics may require different behavior.

This is a future implementation slice, but ADR-0002 reserves the boundary now.

Exact-form degradation preserves NFC-normalized surface spelling and case, consistent with ADR-0001 exact-surface anchors; it does not reuse caseless lemma normalization to manufacture equality. Unknown-language anchors are document-scoped and cannot become global lexical keys. Exact matching means matching the available surface/range representation, not a promise of correct word segmentation for every script.

The question:

```text
Is French supported?
```

is too coarse.

The architecture instead asks:

```text
Is French supported for this feature?
```

### Manual exact-form vocabulary saving

Requires:

```text

persistence
```

No dictionary or lemma provider is mandatory.

### Lemma-aware occurrence grouping

Requires:

```

### Form explanation

Requires:

form-analysis provider

Requires a policy-defined combination such as:

# 48. Vocabulary Preparation Becomes a Derived Feature Capability

The current code says:

```swift
guard language == .english || language == .german else {
    unsupportedLanguage
}
```

That should disappear.

Instead:

```text
resolved language
      ↓
language runtime
      ↓
featureAvailability(.vocabularyPreparation)
```

The runtime determines whether preparation is:

```text
available
degraded
unavailable
```

and why.

This automatically keeps language selection, service composition and product behavior coherent.

# 49. Degraded Preparation Is an Explicit State

Missing linguistic evidence does not necessarily mean the whole workflow must stop.

ADR-0001 already allows unresolved/ambiguous lexical candidates to use restricted assessment policies.

Therefore ADR-0002 permits:

```text
vocabulary preparation = degraded
```

where validated.

But degraded mode must never masquerade as full mode.

A runtime can report, for example:

```text
language: German
definitions: available
frequency: available
lemma/POS model: unavailable
lexical identity: exact-form / direct-evidence-heavy
preparation: degraded
```

Whether a degraded mode is user-visible in production is a release-policy question that requires validation.

It must not be silently treated as equivalent to normal operation.

Feature availability and an individual definition result are separate gates. A registered German dictionary may be temporarily offline; an English lookup may have no entry. Neither an error string nor “No local definition is available” counts as a revealed definition. Without a usable definition, do not accept the post-reveal “My meaning was correct” action or persist verified-known evidence; offer retry/skip and preserve already recorded evidence according to the existing assessment contract. Newly validated degraded modes must define which actions remain meaningful. No new automatic unknown/known classification is introduced by this ADR.

# 50. Introduce Stable Provider Descriptors

Every language-sensitive provider should expose stable provenance.

Conceptually:

```swift
package struct VocabularyProviderDescriptor:
    Codable,
    Hashable,
    Sendable
{
    let id: String
    let version: String
    let supportedLanguageRanges: [VocabularyLanguageRange]
}
```

Examples:

```text

dictionary.de-wiktionary
difficulty.ecdict-frq
difficulty.leipzig-deu-news
morphology.apple-natural-language
morphology.german-deterministic-v1
forms.german-v4
```

Provider IDs must describe semantic data sources, not implementation class names alone.

# 51. Resolve the Language Runtime Once Per Document/Session

The catalog must not run provider selection for every token.

The flow should be:

```text
document
    ↓
resolve language
    ↓
resolve VocabularyLanguageRuntime once
    ↓
pass concrete providers into index/coordinator
    ↓
process N occurrences
```

This maintains effectively linear linguistic processing and keeps the hot loop free of service-location overhead.

### One owner and one revision per active language decision

Extend `ReaderVocabularyState` as the authoritative in-memory owner for Document Session language selection/resolution and its monotonically increasing language revision. `VocabularyPreparationCoordinator` sends selection intents; it does not hold a conflicting mutable language fact. Auto is a selection mode, never a language tag. The v1 manual preparation choice applies to the active Document Session's vocabulary features for both renderer families; switching back to Auto explicitly requests fresh resolution. Cross-launch override persistence is deferred, rather than hidden in an unrelated preference.

Resolve one immutable runtime per `(document ID, load/text generation, language revision, capability revision)`. Increment the relevant revision on manual language change, accepted re-detection, or asset/provider change. Cancel old index, lookup, preparation, cache-publication, and backfill work; cancellation alone is insufficient. Before applying results, verify the captured revisions, request ID, record identity, and that the owner is still open. Rebuild affected derived state through existing text/index/coordinator owners. A worker cannot resolve a different provider midway through a document build.

Changing the current document language does not relabel existing Vocabulary Records or make them eligible for a different-language backfill. Their stored identity is a historical fact; correcting it requires an explicit, separately validated record operation.

# 56. Preserve Full Lexical Identity Through Export Models

`VocabularyExportRecord` currently drops too much semantic identity.

The target model should preserve at least:

```text

when available.

```text
word

Also migrate `ReaderWindowController+VocabularyListExport.swift` → `VocabularyExporter.Record` → CSV/Markdown serialization. # 57. Cross-Document Aggregation Must Fail Closed

The library aggregation hierarchy should be:

```text
1. validated resolved lexical key available
      → group by that key under compatible identity semantics

2. reconciled language + lemma + POS with resolution provenance
      → reconstruct the same validated resolved key, then group

3. language known but lexical identity unresolved
      → document-scoped unresolved grouping; preserve anchor/surface distinctions

4. language unknown
      → do NOT merge across unrelated documents by spelling alone
```

This directly prevents:

```text
en|die|verb
de|die|determiner
```

from becoming one vocabulary entry.

Aggregation is a read-only projection with exact member record IDs and document IDs retained for actions. Unknown/ambiguous POS is not a resolved lexical item; a tuple does not justify promotion merely because fields exist. `.unknown` is unresolved; `.other` retains ADR-0001 semantics and needs the same reconciliation evidence as any permitted POS. Only validated resolved keys with compatible normalization/sense semantics may group globally. Otherwise default to document-scoped unresolved groups, retaining anchor/surface distinctions; do not attach unresolved records to a resolved group by spelling.

Changing the grouping key must update delete, favorite, selection restoration, review/SRS updates, and “already saved” membership consumers together. Every mutation targets the displayed group's exact membership and appropriate learning owners, with the shared-owner constraint in §59. A German group action must not delete or update an English homograph through the old bare-lemma mutation path. A language-aware display alone is not acceptance.

# 58. Unknown Legacy Records Must Not Be Assigned a Language From Spelling

For a legacy record lacking explicit language:

```text
word = "die"
```

does not provide sufficient evidence to infer:

```text
English
```

or:

```text
German
```

Possible recovery sources are, in order:

```text
resolved lexical key
explicit stored language
source-document language metadata
re-analysis of sufficiently rich document/context evidence
```

If language remains uncertain, the record stays language-unresolved.

False separation is preferable to a destructive cross-language merge.

Recovery sources are candidates to validate, not a blind precedence chain. Conflicting stored language and lexical key quarantine the identity from cross-document grouping/provider use until explicitly repaired. Context recognition and current document language may guide a reversible display/lookup decision; they must not silently become durable language metadata on a read. Legacy values possibly produced by the old English fallback are not authoritative proof of English. Without compatible provenance, retain unresolved isolation.

# 59. Legacy Migration Must Be Non-Destructive

ADR-0002 does not authorize rewriting all historic user vocabulary when a new linguistic engine ships.

Migration should be lazy and additive where possible:

```text
old record
    ↓
language missing
    ↓
safe evidence available?
    ├─ yes → enrich metadata
    └─ no  → preserve unresolved
```

Original occurrence identity, SRS history, answers and user edits remain intact.

Cover both `StoredPDFWordRecord` and `StoredWebWordRecord`, SQLite schema/select/bind/upsert paths, JSON backup/fallback decoding, import/export, and record-copy/update initializers. Adding optional Swift fields alone does not persist them. New schema writes must be additive and transactional, with failed migration leaving original data recoverable; verify reopen and retry using isolated real stores.

Preserve UUIDs, stable occurrence keys, annotations/locators, SRS history, answers, and user edits. Nullable metadata must survive all update paths, and typed lexical-key parsing must validate escaping and language/POS consistency. Do not split keys with an unvalidated delimiter heuristic. Preserve existing stored key bytes; a new typed value's Codable shape must not change legacy string fields. If older application versions drop new fields on rewrite, document that downgrade limitation and keep unresolved fallback safe rather than promising lossless downgrade.

Two existing behaviors need explicit handling:

- `WebWordRecordMetadataRepair.repair` is invoked and persisted during library loading, and can rewrite grouping IDs without lexical metadata. Make library loading a read-only projection for this path; any retained explicit repair must be identity-aware, idempotent, and preserve existing occurrence/vocabulary IDs.
- `WordRecordSQLiteStore.insertNormalizedPDFRecord` can absorb a resolved record into a legacy lemma-only wildcard while discarding lexical key/POS. Its current lookup plus `INSERT OR REPLACE` is not a migration contract. Add an atomic store operation that locates an existing occurrence by original UUID and stable source occurrence identity across vocabulary owners **before** choosing a vocabulary row. An existing occurrence retains its UUID, vocabulary/learning owner, answer and SRS; attach new linguistic evidence as additive occurrence metadata without reparenting it. A retry with a fresh incoming UUID but the same unambiguous source occurrence targets that original occurrence. Ambiguous source matching fails without a write. Only genuinely new occurrences may create a separate resolved vocabulary row instead of joining the legacy wildcard. No implicit owner split, duplicated occurrence, or orphan-owner cleanup is permitted as a side effect of enrichment.

PDF answer/SRS state lives on `pdf_vocabulary_words`, shared by its occurrences. Therefore retain a typed learning-owner identity in projections as well as exact occurrence/document membership. An occurrence with newly resolved evidence under a legacy shared owner must **not** become an independently mutable resolved review group. Keep that entire owner in one document-scoped unresolved learning group, with occurrence evidence available separately, until an explicit history-preserving separation is designed. Group membership for answer/SRS edits and undo must be closed over the learning owners it mutates; score each owner once. Occurrence-local actions still target exact occurrence IDs. This keeps old learning history intact while new independent owners can participate in resolved lexical grouping.

Required store fixtures include two occurrences sharing a legacy owner, evidence enrichment of only one, review/edit/undo/save/reopen, and retry with both original and fresh UUIDs. Expected results: one preserved shared learning group, unchanged owner association, no duplicate occurrence, no independently displayed group whose state changes indirectly, and no lost evidence. Repeat full-save/upsert in both input orders. New resolved owners and known-different languages remain isolated. The Web path must preserve its own existing learning-owner relationship under equivalent tests.

These are required decisions at the storage seam, not permission for a general database rewrite.

# 60. Backfill Jobs Must Be Language-Aware

A dictionary/frequency backfill item should no longer be only:

```text
record ID + word
```

It should carry or resolve:

```text
record ID
language
lexical/surface identity
provider profile
```

A German record cannot enter an English metadata backfill merely because both contain the same spelling.

# 61. Backfill Completion Must Be Versioned

Replace the conceptual Boolean:

```text
frequencyBackfilled = true
```

with a completion identity or fingerprint.

For example:

```text
language = de
provider = difficulty.leipzig-deu-news
providerVersion = 2025-1M-top-200000
normalizationVersion = 1
```

A provider change then causes a new backfill when appropriate.

An unrelated old completion marker does not suppress it.

Completion is per compatible work scope and item coverage, not just a document/provider tuple. Include a record-set revision or track eligible record IDs so words added after completion still receive enrichment. Record terminal not-found separately from retryable error, cancellation, and unavailable capability; these latter outcomes must not mark work complete. Revalidate record language and user-edited fields before committing. Enrichment must not overwrite a nonempty user answer or a newer record edit. Existing automatic backfill remains its own explicit workflow; viewing the library must not become a migration write trigger.

Backfill completion is committed only after its matching data write succeeds, transactionally where the store supports it or via an idempotent retry protocol; a callback being scheduled is not durable completion. Track language/provider/version provenance on derived frequency values, not only on jobs. The current `shouldBackfillFrequency` skips every non-nil frequency, so marker invalidation alone cannot repair incompatible populated values. Provenance-less legacy ranks remain unverified and are excluded from language-specific inference until re-derived; compatible display may retain the raw legacy value explicitly as unverified. Replace only machine-owned derived metadata under the existing mutation workflow, preserving user-authored definitions and edits.

# 62. Caches Must Be Namespaced by Semantic Inputs

Any cached language-sensitive result must include all inputs required for semantic validity.

Depending on the cache:

```text
language
provider/ruleset
provider version
surface
lemma
context dependence
```

may matter.

A cache entry generated for English can never be returned for German because its string happens to match.

Include `VocabularyLibraryBuildCache` and `VocabularyDocumentLemmaIndexSeed` explicitly. The former currently fingerprints records without lexical key/POS; the latter checks text/language but not provider semantics. Add identity/normalization and effective analyzer signatures so metadata-only changes invalidate derived groups/indexes. Library reloads also require latest-request publication guards. Persisted cache entries without the new key schema are misses; transient failure is not a durable negative result.

# 63. Session Compatibility Needs More Than One Algorithm Integer

The current preparation session stores an algorithm version:

```text
v3 stable
v7 experimental lexical reconciliation (v4–v6 superseded)
```

Language-provider composition introduces additional semantic dependencies.

A resumed session may no longer be compatible if:

```text
document language changed
language detection result changed
lexical provider changed
frequency provider changed

# 64. Proposed Preparation Compatibility Fingerprint

Conceptually:

```swift
package struct VocabularyPreparationCompatibilityFingerprint:
    Codable,
    Hashable,
    Sendable
{
    let algorithmVersion: Int
    let language: VocabularyLanguageID
    let fingerprintSchemaVersion: Int
    let languageProfileVersion: String
    let lexicalPolicyVersion: String
    let linguisticProviders: [VocabularyProviderDescriptor]
    let linguisticRuntimeSignature: String
    let difficultyProviderID: String
    let difficultyProviderVersion: String
    let calibrationPackIDAndVersion: String?
    let definitionProvider: VocabularyProviderDescriptor
    let normalizationVersion: String
    let assessmentPolicyVersion: String
}
```

Definitions already participate in post-reveal verification, so their provider semantics belong in the fingerprint. Include actual degraded mode and response/evidence-mapping policy. Include domain resources/selection only if they alter candidate identity, difficulty, question selection, or inference; the current `selectDocumentDomain` preserves candidates and is metadata-only. Persist a canonical ordered representation (or a digest of it), never Swift `hashValue`. Provider lists must have deterministic ordering.

The exact encoding may evolve.

The invariant is:

> A session must not resume latent inference under a materially different semantic model without an explicit compatibility decision.

Compare this semantic fingerprint together with document/text identity and candidate inventory identity before restoring answers, final selection, prediction audits, or any latent inference. A missing old fingerprint is incompatible by default unless a tested explicit migration proves equivalence. Keep incompatible session data recoverable using the archive-before-replace extension below; start a fresh active assessment instead of reinterpreting old evidence. The current session/prior stores do not already provide this recovery. Imported Vocabulary Records/SRS remain untouched. Definition text returned over a network is not frozen by an adapter version: retain the per-question reveal/result identity needed to audit existing evidence rather than re-fetching and rewriting its meaning.

Define one effective model descriptor and derive the narrower session, reader-prior, and calibration compatibility checks from it, rather than maintaining divergent copies of version logic. Session checks additionally bind document/candidate identity; reusable priors do not bind a particular document. Legacy calibration packs lacking target metadata are inert unless an explicit reviewed migration binds them to that exact target.

### Compatibility projections and recovery

The fingerprint describes consumed semantic dependencies, not every registered capability or a blanket catalog version. Keep observational provenance alongside it. The `languageProfileVersion` field means the relevant effective profile contract, not a bump caused by adding an unrelated language. Compare the following projections explicitly:

| Change | Stale work / derived data | Session evidence and reader prior |
|---|---|---|
| New document/load/text generation or closed owner | Reject pending publication; rebuild document snapshots/indexes | Reuse a document session only against matching text/candidates; cross-document prior remains eligible when its model matches |
| Manual/automatic language revision with unchanged effective language/model | Reject old in-flight work; rebuild affected projection | No reset solely for changed provenance if semantic and candidate checks pass |
| Effective lexical provider, used Apple runtime/scheme signature, normalization or reconciliation policy | Rebuild linguistic index/seeds and dependent caches | Incompatible unless a tested compatibility rule establishes equivalence |
| Difficulty scale, calibration pack, verification/definition or evidence-mapping semantics | Rebuild affected results and invalidate pending consumers | Invalidate affected session inference and model-dependent prior |
| Form label/display localization or unrelated profile added | Refresh only affected presentation/cache | No inference reset |
| Current metadata-only domain selection | Refresh metadata projections | No inference reset; future model-affecting domain policy requires a semantic version |

For Apple models with no observable content version, the recorded runtime signature is a conservative proxy, not proof of identical model bytes. Do not promise detection of silent model changes. Persisted candidate/evidence identity provides an additional check; readiness claims still require runtime characterization.

Extend `VocabularyPreparationSessionStore` with a versioned envelope at its existing document-scoped key: active session plus archived incompatible payloads. Decode legacy raw sessions, preserve their bytes, and encode archive plus fresh active state together before replacing the value. Encoding failure leaves the old value untouched; callers must not report a saved replacement on failure. UserDefaults has no application-level durable transaction acknowledgment, so do not claim crash-durable archival beyond that backend's guarantees. If a stronger durability requirement is adopted, migrate this concept into the existing durable store in a separately verified slice rather than silently adding another store.

Extend `VocabularyReaderPriorStore` with archival rows in its existing SQLite database, transactionally archiving the old posterior/eligibility state before replacement. Preserve contribution deduplication records and ensure retries cannot recount prior completions. Archive only on incompatible replacement, once per distinct payload/compatibility identity; unchanged saves create no archive copies. Retain archives through this migration until the corresponding explicit user reset/clear; history retention policy changes are separate work. If archiving fails, abort replacement and keep the old state ineligible rather than consuming it. Tests must complete a fresh session and then retrieve the archived old session/prior after reopening.

Carry the effective compatibility identity through `VocabularyResearchEvidenceRecord`, its store/export schema, and `scripts/fit_vocabulary_calibration.py`. The fitter must reject unknown or mixed incompatible observation semantics, or explicitly partition them before fitting; a target label on the output pack cannot repair mixed input evidence. Until these paths are updated, new-fingerprint evidence is ineligible for calibration, while existing historical artifacts remain unchanged. This adds provenance and validation only; it neither authorizes collection nor enables an unreviewed pack.

# 65. Allocate New Protocol Versions; Do Not Reuse v5

The baseline has stable v3 and experimental lexical reconciliation v7. Versions v4–v6 have historical meaning and must not be reused for ADR-0002. Allocate fresh protocol versions when implementation lands, in coordination with ADR-0001 and existing session/prior tests; this proposal does not reserve a guessed number.

Ship semantic fingerprint checks with the first change that affects assessment inputs, not after provider migration. Keep stable and experimental release policies distinct. A language-boundary refactor does not promote experimental reconciliation or authorize a new empirical calibration. The algorithm integer remains useful, but is not the only compatibility information.

# 66. Reader Priors Remain Language-Scoped

Current reader-prior storage already receives a language code.

ADR-0002 strengthens this requirement.

A learner's German vocabulary estimate must never initialize an English assessment merely because the difficulty scale happens to have similar numeric parameters.

The current store already retains algorithm version and contribution IDs. Extend prior compatibility now with the relevant assessment/difficulty/calibration/lexical semantics; language alone is insufficient when providers change. An incompatible prior contributes no latent inference, but remains recoverable. Keep transactionality and idempotent contribution IDs so reopen, cancellation, retry, or fresh session initialization cannot count the same completion twice. Existing eligibility/evidence thresholds remain unchanged.

```text

```

# 73. Mixed-Language Documents Are a Future Requirement, Not a Current Shortcut

The current architecture largely assigns one vocabulary language per document.

This remains acceptable for ADR-0002 v1.

However, APIs introduced now must not make document-level language impossible to refine later.

Research on code-switched text treats token- or turn-level language identification as a distinct problem, and word-level identification is required when languages are mixed within sentences.

Therefore future evolution may add:

```swift
VocabularyLanguageSegment {
    sourceRange
    languageResolution
}
```

or occurrence-level language evidence.

---

# 74. Do Not Solve Mixed-Language Documents by Calling Them `mul`

A document such as:

```text
English narrative
French quotation
English narrative
```

does not have one useful lexical language called “multiple”.

The eventual model should be:

```text
document-level dominant language
+ local language segments/occurrences
```

when evidence justifies them.

This aligns with BCP 47's recommendation not to use `mul` where separate language tags can be represented.

---

# 75. Segment-Level Detection Must Also Be Conservative

Recent research emphasizes that realistic code-switching language identification remains difficult, especially when scaling across many languages.

Therefore ADR-0002 does not authorize aggressive sentence/token switching based on weak evidence.

The same monotonic principle applies:

```text
strong local evidence
    → local language override

weak evidence
    → retain broader context / abstain
```

Mixed-language support receives its own validation work before affecting lexical identity.

# 76. Immediate Phase 0 Correctness Patch

Before the full architecture is implemented, the following changes should be made because they remove current cross-language risk:

```text
1. Stop mapping failed/unsupported language detection to English.

2. Make preparation fail explicitly on undetermined or non-preparation
   languages instead of allowing them to become English.

3. Change DocumentVocabularyFrequencyProvider so unknown languages
   return unavailable/error rather than English.

4. Route dictionary backfill explicitly by resolved language.

5. Prevent German records from querying ECDICT and English records
   from falling through to German Wiktionary.

6. Pass language explicitly to dictionary metadata/frequency backfill.

7. Remove default `.english` arguments from language-sensitive Core APIs.

8. Prevent cross-document library aggregation from merging records
   whose known languages differ.
```

These changes do not require the complete catalog first.

They establish the fail-closed invariant immediately.

Treat this list as desired containment outcomes, not eight independent commits in this order. First add the minimal explicit resolution/request context needed to compile consumers; then route providers and disable unsafe unresolved backfills; then propagate identity into record/export/action paths before enabling global aggregation. A temporary safe library behavior is document/record isolation, not guessing language.

Every slice includes its cache invalidation, async revision checks, and session/prior compatibility gate before changed results can be consumed. Sections 77–81 are work packages with these dependencies, not permission to postpone safety until Phase 5. These containment fixes do not depend on completing ADR-0001 or building the full catalog.

# 85. Required Core Invariants

The implementation is accepted only if all of the following hold.

**L1. Unknown language is never represented as English.**

**L2. A detected but unsupported language retains its real language identity.**

**L3. No language-sensitive API has an implicit English default.**

**L4. A provider may never silently process a request for an incompatible language.**

**L5. Missing capability reduces functionality; it never substitutes an unrelated language.**

**L6. Provider fallback may only occur within explicitly declared compatible BCP-47 ranges.**

**L7. Language detection and product capability resolution remain separate operations.**

**L8. Apple model availability is runtime capability state, not language identity.**

**L9. Resolved lexical identities contain concrete language identity.**

**L10. Undetermined-language exact-form operations remain possible without manufacturing lexical language.**

**L11. Vocabulary difficulty is provided only by an explicitly compatible source.**

**L12. Dictionary definitions are provided only by an explicitly compatible source.**

**L13. Cross-document vocabulary aggregation never merges known-different languages.**

**L14. Language-sensitive caches are namespaced by language and semantic provider version.**

**L15. Existing user data remains readable and is not destructively reinterpreted.**

**L16. Adding a language profile cannot change existing languages unless its registration explicitly overlaps their ranges.**

**L17. Product UI derives language feature availability from the same composition data as runtime routing.**

**L18. Better linguistic evidence may increase capability/resolution coverage; missing evidence may only degrade or abstain.**

**L19. A language/provider revision change invalidates stale async publication even within the same document load.**

**L20. Language-aware grouping and every group action operate on the same exact record membership.**

**L21. No verified-known evidence is manufactured from a failed or missing definition.**

**L22. Compatibility gates ship with semantic changes and cover sessions, priors, calibration, caches, and backfills.**

**L23. Queries do not silently migrate user data; language corrections never rewrite historic records implicitly.**

# 92. Rejected Alternative: Global Shared Registry

Rejected.

Reasons:

```text
hidden dependency
difficult deterministic testing
runtime mutation risk
conflicts with existing composition-root direction
makes experiments harder to isolate
```

Inject the catalog/runtime instead.

---

# 93. Rejected Alternative: English as Universal Safety Fallback

Rejected.

English is not linguistically neutral.

Cross-language substitution can corrupt:

```text
lemmas
definitions
frequency
difficulty
forms
library identity
```

The correct universal fallback is:

```text
language-independent exact-form behavior
```

not English.

---

# 94. Rejected Alternative: Constrain Detection to Supported Languages

Rejected.

It can transform:

```text
unsupported actual language
```

into:

```text
incorrect supported language
```

and therefore converts lack of capability into false certainty.

Detection must be free to identify a language that the product cannot yet analyze.

---

# 95. Rejected Alternative: One `isSupported` Boolean

Rejected.

English and German themselves demonstrate that capabilities have different sources and degradation properties.

French already has more low-level capability than a Boolean `false` would imply.

Italian already has less trusted lemma capability than Apple API presence would imply.

Capability vectors represent reality better.

---

# 96. Rejected Alternative: Dictionary as the Central Language Provider

Rejected.

A dictionary is only one resource.

Some languages may have:

```text
good morphology
no bundled dictionary
```

or:

```text
good dictionary
weak POS analysis
```

The language profile composes independent capabilities.

---

# 97. Rejected Alternative: Let Every Call Site Switch on Language

Rejected.

This produces the current architecture:

```text
switch in form labels
if in definitions
ternary in frequency
fallback chain in dictionary backfill
hard-coded UI list
hard-coded preparation guard
```

These switches eventually disagree.

Provider selection belongs in one composition boundary.

Language-specific implementation logic remains inside each provider.

---

# 98. Rejected Alternative: Immediately Change All Normalization

Rejected.

The existing German-locale normalization is not a suitable future multilingual rule, but changing stable persisted keys without a migration can damage user data.

Normalize architecture first.

Migrate identity semantics only through a separately versioned change.

---

# 99. Rejected Alternative: Solve Mixed-Language Reading Now

Rejected for ADR-0002 implementation scope.

The architecture must allow future segment-level language identity, but shipping a weak code-switching detector now would recreate exactly the epistemic problem ADR-0001 is correcting.

Document-level language plus explicit manual override remains the first release model.

Those may build on this boundary later.

# 101. Positive Consequences

The architecture makes several classes of bug structurally harder.

Adding French no longer risks accidentally receiving:

```text
ECDICT definitions
English frequency ranks
English form grammar
```

because absent capabilities have explicit representation.

The same architecture lets different languages use very different linguistic engines.

For example:

```text
English → Apple + deterministic rules
German  → Apple + lexicon + Wiktionary flexion
Russian → future dedicated morphology provider
Italian → future alternate lemmatizer
```

without changing adaptive assessment semantics.

---

# 102. Negative Consequences

The system gains additional domain types and states:

```text
resolved language
undetermined language
registered capability
runtime availability
degraded capability
release readiness
provider provenance
```

This is more code than:

```swift
if german { ... } else { english ... }
```

Some existing workflows will reveal previously hidden uncertainty.

A user may occasionally see:

```text
language could not be determined
```

where the current application silently says English.

That loss of apparent simplicity is intentional.

The previous simplicity came partly from treating uncertainty as fact.

# 104. Success Criteria

ADR-0002 is successful when all of the following can be demonstrated.

A German `Gift` cannot receive an English ECDICT definition through generic backfill.

A French document detected as French cannot receive an English difficulty prior merely because French preparation is unavailable.

An Italian document can remain Italian while its untrusted lemma provider is disabled.

A clean macOS system missing optional linguistic assets still preserves the correct language and degrades safely.

English and German preparation continue to function with equivalent intended behavior.

Adding a French language profile does not require editing English or German routing code.

The vocabulary library does not merge lexical records across known-different languages.

A provider can be replaced or versioned without hiding the change from preparation-session compatibility.

The UI can describe language availability from the same catalog that actually supplies the services.

And most importantly:

```text
more language evidence
    → more useful capabilities

less language evidence
    → fewer/degraded capabilities

never:

less capability
    → pretend the language is English
```

# 105. Final Decision

Adopt an **explicit-language, capability-based, fail-closed multilingual architecture**.

Normatively:

1. LangReader language identity uses a BCP-47-backed `VocabularyLanguageID`, not `NLLanguage` and not a closed language enum.

2. Automatic language detection returns resolved evidence or an explicit undetermined state. It never defaults uncertainty to English.

3. Detection remains independent of which languages the vocabulary product currently supports.

4. `NLLanguage` and `NLTagger` become implementation details of the Apple NaturalLanguage provider boundary.

5. All language-sensitive Core APIs require language explicitly; implicit `.english` defaults are removed.

6. Language capabilities are granular and independently optional.

7. Provider registration, runtime availability and product release readiness are separate concepts.

8. Language profiles are composed through an injected catalog at the application composition root; no global mutable/shared service-locator registry is introduced.

9. Provider matching may fall back only within explicitly declared compatible BCP-47 language ranges. Cross-language fallback is forbidden.

10. Missing providers return unavailable/degraded behavior; English is never a generic fallback provider.

11. Definition and difficulty/frequency are separate semantic capabilities even when backed by the same dataset.

12. Vocabulary preparation becomes a derived feature capability rather than a hard-coded EN/DE check.

13. Apple NLP asset absence changes capability availability, not language identity.

14. Language identity and resolved lexical identity are propagated through persistence, export and library aggregation.

15. Cross-document library records with different known languages may never merge by spelling/lemma alone.

16. Legacy records with unresolved language remain unresolved unless safe evidence is available; language is never guessed from spelling.

17. Language-sensitive caches and backfills are namespaced by language, provider and semantic version.

18. Preparation-session and reader-prior compatibility include language/profile/provider/calibration/evidence semantics before any changed model is consumed; historical protocol versions are never reused.

19. Existing EN/DE persisted canonical keys remain stable during the initial migration.

20. The current global German-locale normalization policy is recognized as multilingual architectural debt and must become versioned before broader language identity depends on it.

21. Mixed-language segment support remains future work, but new APIs must not assume document-level language can never be refined.

22. The immediate implementation eliminates unsafe dictionary, frequency, detection and library routing with identity propagation, exact-member actions, async revision checks and compatibility gates in the same vertical slices, before adding any new full preparation language.

# 106. Research and Standards Basis

**[IETF BCP 47 / RFC 5646 — Tags for Identifying Languages](https://www.rfc-editor.org/rfc/rfc5646).** Provides the standard language-tag model adopted for `VocabularyLanguageID`, including language/script/region distinctions and guidance for `und` and `mul`.

**[RFC 4647 — Matching of Language Tags](https://www.rfc-editor.org/rfc/rfc4647).** Defines language-range matching and progressive lookup while requiring applications to explicitly define no-match behavior. It motivates same-language range resolution without justifying unrelated-language substitution.

**[Apple Natural Language — `NLLanguageRecognizer`](https://developer.apple.com/documentation/naturallanguage/nllanguagerecognizer).** Confirms that recognition can produce a dominant language or multiple language hypotheses independently of LangReader's product support.

**[Apple Natural Language — `NLTagger.availableTagSchemes`](https://developer.apple.com/documentation/naturallanguage/nltagger/availabletagschemes(for:language:)).** Establishes that linguistic tag schemes are runtime/device capabilities and that missing assets can be requested separately. This supports modeling runtime availability independently from language identity.

**[Apple Foundation — `Locale.Language`](https://developer.apple.com/documentation/foundation/locale/language).** Provides BCP-47-aware language components, identifiers and language relationships suitable for implementation behind LangReader's stable domain wrapper.

**[Unicode case-mapping guidance](https://www.unicode.org/versions/latest/core-spec/chapter-3/#G33992).** Distinguishes language-sensitive casing from language-neutral case folding and specifically documents Turkic/Greek special cases, supporting removal of a globally German-specific lowercasing policy before broad multilingual identity depends on it.

**[Universal Dependencies morphology/tokenization model](https://universaldependencies.org/u/overview/tokenization.html).** Separates lemma, POS and morphological features while explicitly recognizing language-specific tokenization/fused-word behavior. This supports the profile-owned linguistic-evidence boundary rather than a universal `NLTagger`-only model.

**[Brysbaert, Mandera & Keuleers (2018), _The Word Frequency Effect in Word Processing: An Updated Review_](https://biblio.ugent.be/publication/8555760).** Reviews quality differences among frequency estimates and variation associated with language exposure, supporting explicit provenance and validation of difficulty sources.

**[van Heuven, Mandera, Keuleers & Brysbaert (2014), _SUBTLEX-UK_](https://www.tandfonline.com/doi/abs/10.1080/17470218.2013.850521).** Shows that a British-specific frequency resource predicts British lexical-decision data better than SUBTLEX-US in the reported comparison, demonstrating that even same-language corpus substitution is not automatically neutral.

**[Jhamtani, Bhogi & Raychoudhury (2014)](https://aclanthology.org/Y14-1041/) and [Rijhwani et al. (2017)](https://aclanthology.org/P17-1180/).** Study word-level identification in code-switched text. They motivate the future occurrence/segment seam; they do not validate a document-reading detector for Leaf Reader.

**[Burchell et al. (2024), _Code-Switched Language Identification is Harder Than You Think_](https://aclanthology.org/2024.eacl-long.38/).** Finds realistic multilingual code-switch identification difficult and studies sentence-level multi-label identification. This supports caution; postponing segment-level routing is a product decision, not a result proving all segment detectors inadequate.

# 107. Repository-Specific Principle

ADR-0001 established:

```text
classifier output != lexical identity
```

ADR-0002 establishes the analogous rule one level earlier:

```text
detector/provider availability != language identity
```

Together:

```text
language evidence
    != language capability
    != lexical evidence
    != lexical identity
    != learner knowledge
```

Each transition requires its own explicit contract.

That separation is the foundation on which LangReader can become genuinely multilingual without duplicating its learning engine or silently contaminating one language with another.
